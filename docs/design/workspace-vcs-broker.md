# Workspace and VCS broker design

Status: implementation contract

Scope: opt-in multi-project workspaces for broker profiles, plus host-executed Git and GitHub CLI access from synchronized guest projects. Existing single-project broker and virtiofs profiles keep their current behavior.

## Decisions

1. `workspace.mode: workspace` selects a bounded collection of projects. `workspace.root` is a host routing root. `workspace.selectors` are relative glob patterns, defaulting to `apps/*` and `tools/*`. Only matching directories are sessions. A selector cannot escape the root, and duplicate or nested matches are rejected.
2. Cloister coordinates the collection through the existing `SyncBroker` session API instead of generating `mutagen.yml`. This preserves the tested isolated Mutagen daemon, SSH wrapper, status parser, policy hash, and rollback behavior. The collection has the same start, flush, pause, and terminate semantics as a Mutagen project: each action applies to every named session and fails closed if any session is unhealthy.
3. Every project is synchronized as a whole directory. Discovery does not use `git ls-files`, so tracked files, untracked files, and local directories participate unless an ignore rule excludes them.
4. Every session uses `two-way-safe`, portable symlinks, accelerated scanning, the host's native watcher, `probeMode: assume`, `maxEntryCount`, and `maxStagingFileSize`. The default entry limit is 200,000 per project. The initial full scan is bounded by the project root and the limit.
5. `.git` is always excluded. Git and `gh` invoked in a mapped guest project execute on the host through an authenticated loopback command service and an SSH reverse tunnel. Host Git continues to run normally against the same repository.

## Configuration

```yaml
profiles:
  work:
    start_dir: ~/Code/1-800-Battery
    workspace:
      mode: workspace
      root: ~/Code/1-800-Battery
      selectors:
        - apps/*
        - tools/*
      max_entry_count: 200000
      max_staging_file_size: 2 GiB
      project_ignore:
        tools/rockauto-scraper:
          - data/raw/
        apps/example:
          - .local-generated/
```

`root` defaults to `start_dir`. Empty selectors use `apps/*` and `tools/*`. `max_entry_count` and `max_staging_file_size` apply to each session. `project_ignore` keys are clean project paths relative to `root`, not patterns. Unknown keys are rejected so a typo cannot silently omit a safety rule.

Single-project `mode: broker` continues to use `start_dir` as its one session root and `workspace.ignore` as its extra rules. `mode: virtiofs` remains unchanged.

## Session model

For every discovered project, Cloister calls the existing stable session builder. The host endpoint is the canonical project directory. The guest endpoint is `~/workspaces/<sanitized-name>-<path-hash>`. The hash prevents collisions between projects with the same leaf name and remains stable across restarts. The session name contains the profile identifier and the same opaque project identifier.

The ordered ignore policy is intentionally small:

1. Profile `workspace.ignore` rules, parsed by the existing ignore compiler.
2. Rules from the exact `project_ignore` entry. Project-specific output directories (for example a scraper's `data/raw/`) are expressed here rather than hardcoded in Cloister.
3. Mandatory `.git` and `node_modules` exclusions, appended last so negation cannot re-include them.

Workspace mode does not import repository `.gitignore` files because those files commonly hide local build and runtime inputs that still need to exist in the guest. It also does not add generic build, cache, coverage, distribution, virtual environment, or generated-output exclusions. Such content remains available to build, test, deploy, commit, and run unless the profile explicitly excludes it. Ignored paths are not scanned, transferred, or deleted by Mutagen, so a guest-local `node_modules` survives synchronization.

Activation creates every safe guest root, creates or resumes every session, then flushes and verifies every session before entry. Partial activation is rolled back by pausing every session that was touched. Quiesce flushes and verifies each active session before pausing or terminating it. A session already paused with no reported conflicts or endpoint problems is already quiesced, so Cloister skips its invalid flush and redundant pause. A failure leaves the VM running and reports the project that failed.

The broad `start_dir` traversal refusal is disabled only for `mode: workspace`. The routing root is not mounted or synchronized. Each discovered project still has an independent `maxEntryCount` fail-fast limit. The existing refusal remains for single-project broker and virtiofs modes.

## VCS control and data flow

```text
guest git shim
  -> HTTP request on guest loopback with token, cwd, argv, and selected env
  -> SSH reverse tunnel
  -> host VCS command service
  -> validate and classify the command
  -> account-scoped gh: run from host home without a project barrier
  -> remote-only repo-scoped gh with explicit -R/--repo/GH_REPO: use a mapped project when available, otherwise run from host home
  -> other commands: map guest cwd, lock that project, and flush/verify Mutagen
  -> real host git or gh
  -> for working-tree-mutating commands: Mutagen flush and clean-status barrier
  -> streamed combined output and exact exit code trailer
```

One standalone host service runs per profile and listens on a random loopback port. It follows the same detached host-service pattern as `op-forward` and `cc-clip`: the service has its own process lifetime, its tunnel is detached, and profile lifecycle operations own startup and teardown. A stable service owner groups the profile lifecycle, while every daemon generation has a distinct identity in its argv, private configuration, readiness, activity, transition, log, and spool paths. Tunnel and guest-file ownership use that generation identity. The one profile-scoped state record points to the current generation and is atomically replaced only after a new generation passes its host and guest readiness checks.

Process identity is the recorded PID plus the kernel's boot-relative process start value. Darwin obtains `ri_proc_start_abstime` from `proc_pid_rusage` with `RUSAGE_INFO_V3`; Linux obtains start ticks since boot from field 22 of `/proc/<pid>/stat`. Those ticks typically have 10 ms granularity (`HZ=100`), so two processes started in the same tick record identical start times. Both record the resolved executable path as corroborating diagnostic metadata. Path drift and an unreadable or unparseable argv cannot veto management of a process whose kernel start value matches. When argv is readable and parses as `vcs-broker serve`, a positive mismatch of `--owner` or `--generation` against the expected values is definitive negative evidence and rejects the match. Linux uses `pidfd_open` and `pidfd_send_signal` when available to close the individual-PID reuse check/signal window. Before a raw process-group signal it verifies that the pinned member is still live, re-reads its start value, and re-checks its process group; Linux has no pidfd group-signal operation, so a narrow group-ID reuse window remains after those adjacent checks. Older Linux kernels use the same adjacent identity and group checks without pidfd pinning. Darwin has no identity-qualified signal primitive, so its check is immediately adjacent to the signal and retains a documented residual PID-reuse window.

Every broker and tunnel observation has four outcomes. A matching start value is owned and may be signaled. `ESRCH` is dead and permits stale-state cleanup. A readable different start value is a reused PID, so the stale records may be cleaned but the live stranger is never signaled. A live PID whose start value is absent or unreadable is unverifiable: Cloister does not signal it, remove any service record or guest configuration, or start a competitor. The refusal reports the PID and live command and tells the user to run the exact `kill <pid>` command only after confirming it is stale, wait for exit, and retry `cloister repair`; destructive lifecycle commands surface the same refusal instead of continuing. These guards cover broker stop, force-stop and replacement signals, owned and generic tunnel teardown including `StopAll`, and the child watchdog before its process-group kill. Generation cleanup derives every filename from a strictly validated generation ID and the profile's state directory; serialized cleanup paths are never trusted, symlinks resolving outside that directory are refused, and recursive removal cannot cross it.

Interactive entry, headless entry, and `open` launch a detached ensure helper and continue without waiting for broker recovery. The launcher detaches all three standard streams and, while holding a nonblocking attempt on the existing profile lock, records the helper's PID, kernel start time, and executable in the profile state. A second entry skips launch when that exact helper is live or the profile lock is already held. Completion clears the helper identity, stores the timestamp and error in the same profile state, and appends the outcome to the current generation log; `status` and the next entry surface a failure. `exec` ensures synchronously because an arbitrary guest command can invoke `git` or `gh` indirectly, but a wait longer than one second prints progress and failure remains a warning rather than blocking VM access. `create`, `repair`, `rebuild`, `reset`, `resize`, `snapshot`, and `add-stack` also ensure synchronously after the VM operation so their completed lifecycle state includes an attempted broker reconciliation. `stop`, `delete`, `rebuild`, `reset`, `resize`, `snapshot`, and an `add-stack` restart synchronously stop the broker before stopping or destroying the VM. Generic `tunnel.StopAll` deliberately skips both current broker-owned claims and legacy broker PID records so a future lifecycle caller cannot bypass the broker drain. The service remains available with no interactive session and therefore supports a headless guest agent.

Ensure-and-deploy is serialized by a per-profile host `flock`. Acquisition is bounded at 12 seconds. The lock covers state inspection, repair or transition requests, and a dead process's bounded startup; it never covers a graceful drain. A caller that finds an intentional drain receives a retryable warning instead of waiting behind it. Starting a new service has a 30-second readiness bound, which covers its independently bounded 12-second guest deployment and subsequent bounded guest-path probe. The longest synchronous failed dead-process recovery can take 79.8 seconds of broker coordination: 12 seconds resolving guest home, 12 seconds waiting for the lock, 1.8 seconds for three host probes, 12 seconds for generation-checked stale guest cleanup, 30 seconds for replacement readiness, and a final 12-second generation-checked guest cleanup if startup times out after publishing its generation-local cleanup record. Successful recovery omits the final cleanup and is bounded at 67.8 seconds. Interactive and headless entry do not wait for that work; only their detached helper can incur it. A healthy inspection whose guest endpoint stalls takes less because it does not perform cleanup or synchronous replacement. Workspace discovery and hypervisor operations outside this broker coordination have their own bounds. A workspace-mode change away from the broker requests daemon-owned retirement and returns without waiting for its drain.

The readiness file closes the final publication crash window. Under the profile lock, ensure, retire, and stop scan generation readiness files belonging to that profile before trusting the profile pointer. A `Ready:true` generation is adoptable only when its complete broker state is valid and its PID/start value is owned. Generation order is an explicit monotonically increasing integer copied into configuration, readiness state, and the profile pointer; the highest order is adopted, while duplicate orders are rejected as ambiguous rather than resolved by filesystem mtime. The adopted state is atomically published as the current pointer, so ensure does not start a competitor and stop can target it. Other live ready generations receive the existing graceful shutdown signal and drain before their generation files are removed. A live non-ready generation is reported as startup in progress and blocks a competitor; dead and PID-reused generation artifacts are cleaned through generation-derived paths.

Upgrade from the released session-scoped implementation has one narrow migration exception for its integer-only `tunnel-vcs-broker-<profile>.pid` record. `ensure` and the running daemon apply the same rule: under the profile lock they capture the live PID's kernel identity and retire it only when it is a PPID-1 `ssh` executable whose argv contains the exact fixed guest reverse-forward shape and the selected profile's exact SSH config/key and destination. A dead legacy PID is simply removed. A live process that does not match is left untouched, its record is retained, and repair reports it without signaling. This safely moves the singular guest port to the standalone generation. The daemon takes that profile lock from its guest-verification ticker, waiting at most 12 seconds; it applies the rule on every healthy verification tick (every 60 seconds) even while the owned tunnel is healthy, without replacing that tunnel, and again before every tunnel repair. When a live matching legacy tunnel is retired, Cloister reports that the previous session's now-unreachable in-process broker remains until that session exits. The standalone shim reads only `~/.cloister/vcs-broker-service.env`; deployment removes the released implementation's `~/.cloister/vcs-broker.env`. A released session that later exits can therefore delete only the unused legacy path, and its integer-PID-only `StopNamed` cannot see the generation-owned `.owner.json` tunnel record. The old in-process broker has no independently recorded PID and is not signaled; after its tunnel is retired it is unreachable and exits with its owning legacy session. A released session that starts after upgrade can rewrite the integer PID record; the daemon's ticker retires a matching recreation so a later owned-tunnel death remains repairable.

Health has two separate failure domains. Daemon health is an authenticated request directly to its host loopback port using the recorded token. Cloister makes three attempts, each bounded at 500 ms, with 100 ms and 200 ms backoffs; all three must fail before the endpoint is classified unhealthy, for a maximum 1.8-second host-health delay. An authenticated `503` with `Retry-After` identifies an intentional drain and is not treated as a dead daemon. HTTP silence is not proof that the process or its children are gone: if the owner-checked process is still alive, ensure records a daemon replacement request and returns immediately. The daemon closes admission and drains its accepted commands before replacing itself. A private `0600` activity record lists admitted argv and projects without depending on HTTP, so a wedged-but-busy process is distinguishable from a gone process and the eventual drain-expiry report names exactly what was interrupted. Only an owner-checked process that is actually gone, or a process whose ten-minute drain has expired, is eligible for a process-group force stop.

Tunnel health separately verifies the exact recorded SSH process and then sends an authenticated probe through the fixed guest endpoint. A healthy daemon with a failed tunnel path receives an immediate in-process tunnel-repair request; its PID and token stay unchanged, and command admission is never paused. Repair replaces only the exact tunnel claim, atomically refreshes the guest shims and owner configuration with the existing token, probes the guest path, and publishes the new tunnel PID. Host commands and post-command barriers already in flight continue when the tunnel is swapped. The broken transport may already have lost an in-flight response; that client receives the shim's explicit ambiguous-delivery diagnostic and exit 74 rather than an automatic retry.

The workspace hash covers the guest home, workspace configuration, and derived project session specifications. On a hash mismatch, ensure writes the desired configuration into the current generation's private request path and asks that daemon to apply it; on a build-identity mismatch it allocates a new generation and asks for replacement by the current Cloister build. The request returns immediately while the old broker continues serving its current project set. A pure addition is a strict superset of project specifications in which every existing specification is byte-identical and the guest home, workspace configuration, backend, generation, and build identity are unchanged. The daemon applies that case by building and atomically publishing a new mapper and refreshing the guest shim/config with the existing token while admission remains open. Existing handlers retain the proxy snapshot they already acquired. The per-project lock registry belongs to the server rather than a replaceable proxy, so old and new mapper snapshots still serialize commands carrying the same stable project ID.

Removals, changed project roots or modes, and build or unhealthy-daemon replacement use a closing gate. The daemon returns authenticated `503` plus `Retry-After` before any rejected command executes, and drains the set it already admitted. With no new admissions, steady traffic cannot starve the transition. A same-build configuration change rebuilds and swaps the mapper in process and refreshes upgraded guest shims without changing the token. A process replacement drains first, stops the old generation's exact tunnel, and only then starts the new generation; successful replacement can therefore disconnect guest VCS for up to the 30-second startup bound. A real curl that reaches the fixed guest endpoint during this gap gets connection-refused exit 7 and the shim retries it as pre-delivery. A connection reset after the request was read is not retried and exits 74 as ambiguous delivery. If startup fails, the old daemon restores its own tunnel and reopens admission. Starting the replacement before moving the fixed guest port would require a staged daemon protocol, descriptor passing, or a permanent front proxy; that complexity is disproportionate to a rare upgrade and would create another credential-bearing lifecycle component.

Failed or timed-out transitions reopen the old service and retry with exponential backoff beginning at five seconds and capped at one minute. After five failed attempts the daemon records `failed`, stops automatic retries, and keeps serving the old mapping. The next explicit ensure or `repair` resets the attempt sequence. Entry's detached ensure and `cloister status` surface both retry-pending and failed transitions. The admission-closed window for a successful same-build update is bounded at ten minutes for the longest admitted command plus the bounded guest refresh; successful process replacement adds at most the 30-second startup bound after the drain. The build identity is the embedded Cloister version (or Go VCS build metadata for an unversioned development binary), not a hash of the executable.

Shutdown first stops admitting commands while leaving the listener and reverse tunnel available. New authenticated requests receive `503`, `Retry-After`, and a message telling the caller to retry. Already admitted commands run through the host operation and its post-command Mutagen barrier. Command execution is independent of response delivery. Output is written into an unlinked file in a generation-specific `0700` directory, so `SIGKILL` leaves no named secret-bearing spool; startup also removes any stale entries as a backstop. Storage is capped at 16 MiB per command and 64 MiB for the daemon. At either cap, further output is discarded rather than blocking or killing Git, the command and barrier finish, the real exit code is returned, and the response explicitly states how many bytes were retained. A network write that makes no progress is bounded at 15 seconds, while the deadline slides for a slow reader that continues making progress. Graceful `Drain` also closes and removes an automatically allocated spool directory, so callers do not need a second cleanup call.

The tunnel remains until healthy clients receive the real body and exit-code trailer. Only after the accepted set and response handlers finish does the daemon atomically remove its owned guest configuration, stop its exact tunnel, and exit. The drain bound is ten minutes, chosen to cover realistic authenticated pushes and hooks without allowing VM lifecycle operations to wait forever; the lifecycle controller allows five additional seconds for cleanup. `cloister stop` and other destructive lifecycle operations wait and print the active argv, project, and elapsed time every five seconds. If the drain expires, Cloister records and reports every interrupted command and guest project path, kills the daemon's process group, warns, and continues stopping or destroying the VM. Managed hard-stop paths also target the process group. Each host command also has a sibling watchdog connected to the daemon by a private pipe; if even a raw `SIGKILL` removes only the daemon PID, pipe closure makes the watchdog kill that daemon generation's private process group before the child can continue independently. A prior generation's watchdog cannot target a replacement's distinct process group. A `SIGSTOP` leaves the pipe open and deliberately allows an accepted child to continue: finishing a repository operation is safer than asynchronously killing it midway through mutation.

The daemon checks VM liveness every 15 seconds and exits only after three consecutive negative checks. A positive check resets the count, so one or two backend query failures do not cause shutdown. Confirmation therefore takes at least 30 seconds from the first negative sample and at most 45 seconds after an already-stopped VM is sampled. The daemon then drains, removes guest configuration and its exact tunnel, and removes its state while holding the same profile lock. Normal snapshot, resize, reset, stop, delete, rebuild, and stack-restart paths signal and drain the broker before the backend VM transition, so those transitions do not depend on the liveness fallback.

Every fourth positive liveness sample, once per minute, also verifies that the service environment contains the current generation, endpoint, and unchanged token, that the installed shim's SHA-256 digest matches this build, and that an authenticated health request succeeds through the guest reverse tunnel. Missing, symlinked, or mismatched files are atomically redeployed together with the same token, and the legacy environment path is removed. On a healthy guest probe the daemon takes the profile lock from this ticker, waiting at most 12 seconds, and applies the same narrowly scoped legacy PID-file retirement `ensure` uses; a matching record is retired even while the owned tunnel is healthy, without replacing that tunnel. A live process that does not match is left untouched and the tick reports it. Guest endpoint health must fail three probes, each with a 12-second guest-control bound and 100/200 ms backoffs, before the daemon invokes its existing immediate tunnel repair with admission open. Repair takes the same profile lock and retirement step before replacing the owned tunnel. The detached SSH start is independently bounded at 12 seconds. Repair preserves the daemon PID and token and logs its outcome. With current guest files, working guest-control SSH, and an uncontended profile lock, tunnel death immediately after a check is detected, repaired, and authenticated again within 168.6 seconds: 60 seconds to the next check, 12 seconds to inspect files, 36.3 seconds for the failed probe set, 12 seconds to start the tunnel, 12 seconds to redeploy, and 36.3 seconds to confirm it. A contended lock or a lock-wait timeout defers repair to the next verification tick, adding up to 60 seconds; 168.6 seconds is the uncontended figure, not an absolute maximum. If guest-control SSH remains unavailable, repair waits for a later successful check because neither an authenticated probe nor a guest write can succeed during that outage. VM-stopped samples do not perform either guest check.

SSH exposes the service on a fixed guest loopback port. The service owner writes its random bearer token and generation identity to `~/.cloister/vcs-broker-service.env` and installs the shim through the shared atomic guest writer: payloads are base64 transported and leaf symlinks are replaced rather than followed. The environment file ends mode `0600`; the installed shim is changed to `0755` only after its atomic replacement. Saved real-binary paths also use a sibling temporary file and atomic leaf replacement. A healthy ensure neither regenerates the token nor rewrites the guest file; periodic compatibility repair reuses that token. The endpoint accepts only `git` and `gh`, bounded request fields, and a valid token. Git and implicitly targeted repository commands also require a registered workspace path; account-scoped `gh` and explicitly targeted repository commands do not. It never accepts a shell command string. Arguments are transported as repeated URL-encoded values and passed directly to `exec.Cmd`.

The guest shim transparently retries an authenticated admission-time `503` and curl exits 5, 6, and 7, which mean proxy resolution, host resolution, or connection establishment failed before this loopback HTTP request could be delivered. It honors a numeric `Retry-After` and otherwise backs off from one second to a five-second cap, printing immediately that it is waiting rather than remaining silent. Its total retry budget is 10 minutes 35 seconds, covering the maximum ten-minute drain, 30-second replacement startup, and five seconds of scheduling margin. Once the server admits a request it sends HTTP 200 and never converts execution or barrier failure into an HTTP error. Curl exit 22 is classified using the captured HTTP status: `503` is the safe pre-admission retry above, while other 4xx/5xx responses are definite pre-execution rejection, print that the command did not run, and exit 125. All genuine post-delivery transport failures are treated as ambiguous rather than retried—including partial response (18), timeout (28), empty reply (52), send failure (55), and receive failure (56)—because the host may have received and completed the command. The shim prints instructions to inspect `git status` and `git log` before retrying and exits 74, distinct from retry exhaustion (75) and ordinary broker unavailability (125). This classification follows curl's official [exit-code documentation](https://curl.se/docs/manpage.html#EXITCODES) and [libcurl error definitions](https://curl.se/libcurl/c/libcurl-errors.html).

The guest installs `git` and `gh` shims ahead of the system tools. Inside a registered workspace they call the broker. Outside a registered workspace they execute the saved real guest binary when present. A missing or empty legacy record falls back only to the base-owned `/usr/bin/<tool>`; if neither is available, the shim returns a clear unmapped-workspace error. This client shape and protocol can later add another named VCS executable without changing path mapping or synchronization barriers.

Commands tied to a mapped project flush before execution. A successful flush is a bidirectional convergence barrier, which makes guest edits visible in the host working tree and also imports completed host edits. Commands classified as working-tree-mutating flush again after the host process exits, even when it exits nonzero because a failed merge, rebase, checkout, or download can leave changes. The post-flush result takes precedence over a zero command exit because the guest view would otherwise be stale. Per-project locking serializes commands in the same project, while commands in different projects remain concurrent; there is no healthy-state global admission gate. Account-scoped `gh` commands and explicitly targeted remote-only repository commands issued outside a project have no project tree to synchronize, so they run from host home without a lock or barrier. Repository verbs that can consume, create, or modify local files still require a mapped project even when `-R`, `--repo`, or `GH_REPO` supplies the remote repository. Uncoordinated native host editors cannot be locked; concurrent edits are reconciled by the barriers and fail closed on a Mutagen conflict.

Mutating Git verbs are `checkout`, `switch`, `reset`, `merge`, `pull`, `stash`, `rebase`, `restore`, `clean`, `revert`, `cherry-pick`, `am`, `apply`, `submodule`, `commit`, and `push`. Commit and push receive the post-barrier because host hooks can modify tracked files. Other Git commands get the pre-flush only. This is conservative about guest refresh without making ordinary `status`, `diff`, `log`, `show`, `branch`, or `fetch` wait for an unnecessary second scan. A config-defined override is intentionally omitted until a real command requires one.

## Edge cases

The first protocol implements noninteractive host execution, path mapping, host credentials, host hooks, constrained `gh`, initialized submodules, and synchronization fences. Full PTY and stdin transport, terminal credential prompts, arbitrary interactive editors, TTY-dependent hooks, and interactive conflict tools are explicitly deferred.

| Case | Behavior |
|---|---|
| `git status`, `diff`, `log`, `show`, `branch` | Flush and verify first, execute host Git at the mapped host cwd, stream output, return its exit code. |
| Checkout, reset, merge, pull, stash, rebase, restore | Flush and verify, execute under the project lock, then flush and verify again even after nonzero Git exit. |
| Commit message with `-m`, `-F`, or stdin-free hook | Supported. Git and hooks run on the host with the host repository and configuration. |
| Interactive commit editor | No terminal byte stream is carried by the first protocol version. A commit without `-m`, `-F`, `--message`, or `--file` fails before execution with guidance to supply a message. Only the noninteractive `GIT_EDITOR=true` and `GIT_EDITOR=:` sentinels are forwarded. Arbitrary editors and PTY passthrough are deferred. |
| Other interactive Git modes | The request has no stdin or PTY. Commands such as `git add -p`, `git rebase -i`, and conflict tools fail early with guidance to run the equivalent host command. Noninteractive flags remain supported. |
| Push credentials | Git runs on the host and therefore uses host credential helpers, SSH agent, keychain, and configuration. A credential flow that requires terminal input is unsupported and fails rather than reading guest secrets. |
| Git hooks and signing | Hooks execute host-side in the host repository. Host signing and hook dependencies are used. Hook stdout and stderr are streamed. Hooks requiring a TTY are unsupported. |
| `gh` and PRs | The `gh` shim runs allowed host commands with host authentication. Search, status, `auth status`, `repo list`, and read-only API endpoints without repository placeholders or a `repos/...` path are account-scoped and need no mapped project. Remote-only PR, issue, run, workflow, release, `repo view`, and repository API operations may use `-R`/`--repo` or `GH_REPO` outside a project. Verbs that can use local files—including checkouts, downloads, uploads, file-backed bodies or notes, release assets, and workflow `@file` inputs—always require a mapped project. `gh api` remains restricted to read-only (GET, no request-body fields) because it runs with host credentials and an unrestricted write would allow account-level mutation (SSH keys, repo deletion) from the sandbox; run write API calls on the host. Aliases, extensions, authentication mutation, and repo clone or creation are rejected. Commands that invoke an editor or browser require explicit noninteractive flags. |
| Outside a mapped project | At the workspace routing root, account-scoped `gh` and explicitly targeted remote-only repository commands run from host home. Repository commands that can use local files are refused with guidance to change directory. Bare Git is refused with guidance to use `git -C`; implicitly targeted repository `gh` commands are refused with guidance to use `-R` or change directory. Outside `~/workspaces`, the shim still falls through to the real guest executable when available. No project is guessed. |
| Nested host repository | Mapping preserves the cwd relative path. Host Git discovers the nearest host-side `.git`, so an existing nested repository works. A nested repository created only in the guest cannot work because its `.git` is excluded; initialize it on the host first. |
| Submodule | An already initialized host submodule works because the host has its `.git` file and metadata while its working tree is synchronized. `git submodule update` executes host-side and the post-flush sends changes to the guest. Missing host submodule metadata produces the native Git error. `git submodule foreach` is rejected because it would accept an arbitrary host shell command. |
| Git worktree | A selected worktree is a distinct canonical session. Its host-side `.git` indirection remains host-only and Git resolves it normally. |
| Concurrent host edit | The pre-barrier imports edits completed before Git starts. The project lock blocks other brokered commands. An external edit during Git is not hidden; the post-barrier reconciles it or reports a conflict and fails closed. |
| Host process or tunnel loss | The shim reports broker unavailability and does not invoke guest Git against a metadata-free tree. Git's exit code is preserved when the command ran. |
| Flush or status failure | Git is not run after a failed pre-barrier. A failed post-barrier is reported as synchronization failure, and the original Git exit is included in diagnostics. |
| Unknown command classification | Unknown Git and `gh` subcommands are rejected before host execution. New allowlisted commands that mutate the working tree must be added to the explicit classifier with a test. |

## Failure handling and recovery

- Discovery fails on an invalid selector, an escaping match, a non-directory match requested as a project, nested selected roots, duplicate canonical roots, no projects, or an unused `project_ignore` key.
- A session hitting `maxEntryCount` or `maxStagingFileSize` fails activation with its relative project name. Cloister does not widen the limit automatically.
- A changed or unverifiable ignore policy is never resumed. Cloister logs the recovery, terminates the stale deterministic session, and creates a fresh synchronization history. If termination fails, recreation is refused and the existing session is left for inspection.
- Any workspace activation or quiesce error is annotated with the project path. Destructive VM operations do not continue after an incomplete flush.
- The VCS service rejects traversal, symlink escape, an unknown guest root, an unknown executable, invalid token, oversized request, and NUL-containing fields.
- The shim never falls back to host execution for an unmapped path. It also never falls back to guest Git inside a mapped project because the guest tree has no `.git` contract.

## Verification boundary

Unit tests use temporary project trees, `broker.Mock`, `vm.MockBackend`, and a fake host command runner. They cover discovery, stable session construction, minimal ignore composition, special and per-project ignores, per-session limits, guest-to-host path containment, Git command classification, and flush-run-flush ordering.

Real VM and Mutagen end-to-end verification remains necessary for Mutagen's `probe-mode=assume` CLI behavior, initial multi-session scans, reverse tunnel lifetime, HTTP streaming and trailers through both backends, guest PATH ordering, host credential helpers, hooks, submodules, and conflict behavior under concurrent host edits.

If workspace collections grow into hundreds of projects, generate a private `mutagen.yml` and use `mutagen project` lifecycle calls to reduce subprocess overhead. The engine-neutral session collection is kept deliberately compatible with that replacement. A framed full-duplex transport with PTY allocation can later add interactive editors and prompts without changing host path mapping or Git execution semantics.
